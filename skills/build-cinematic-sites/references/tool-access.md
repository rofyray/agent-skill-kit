# Tool Access and Adaptation

## Separate the decisions

The reasoning host, site implementation platform, image/video model, provider, editor, and browser inspector are independent choices. Preserve the user's selections and discover the capabilities exposed in this session. A brand name alone does not establish which endpoint or operations are available.

Support configured native tools, plugins, connectors, APIs, CLIs, a supported browser editor, or a manual handoff. Check permissions and available interfaces before assuming shell, local files, network, or visual inspection. Do not replace a chosen framework with a single-file page or rebuild an existing site just to fit an example.

Use existing tooling and project checks where possible. Install or connect a dependency only when the task requires it and authorization covers it. For a user-requested connection, use the host and service's current official setup instructions, then verify an appropriate read-only capability. Do not include credentials in prompts, source, logs, manifests, or command arguments.

## Inspect the actual media interface

Before submitting, check the selected tool's current schema for input types, reference roles, aspect ratios, sizes, duration, frame rate, first/end-frame support, masks, alpha, audio, supported controls, and output retrieval. Discover how uploads and asynchronous status work. Do not copy another provider's argument names or assume a web feature is exposed through a connector.

Use a current official capability lookup when documentation is needed. Do not hard-code prices, model rankings, trial allowances, or claims that quoting is always free. When cost estimation is available, use its documented behavior. When exact cost is unavailable, state the uncertainty and obtain a bounded authorization before spending.

Plan the whole useful production unit, including supporting assets and expected retry allowance. Stay within the user's limits without repeatedly asking for already authorized actions. If a submission times out after returning a job ID, inspect that job before resubmitting; ambiguity must not duplicate paid work. Track actual outputs and inspection status separately.

## Capability gaps

| Missing capability | Useful route |
| --- | --- |
| Generator | Use supplied media, controlled graphics, or an explicit prompt/asset handoff. |
| Exact type or UI in the generator | Keep text and interface elements in deterministic page or compositor layers. |
| Long clip or end-frame conditioning | Plan supported segments and controlled transitions, preserving the user's continuity requirement. |
| Video processing | Use an available editor or provide exact processing requirements for the selected tool. |
| Source-file access | Work in the supported site editor, or deliver a complete platform-specific build specification. |
| Runtime or preview | Deliver available source and static checks; mark runtime behavior unverified. |
| Browser inspection | Provide reproducible checks for the user and distinguish implementation claims from observed results. |
| Optional companion skill | Offer its repository location when useful; continue with this skill's self-contained workflow. |

Do not quietly change provider, upload destination, cost tier, or output format. Explain a necessary change only when it materially affects the agreed result or requires a user decision. Continue unblocked work meanwhile.

## Persist and report honestly

Use supported retrieval mechanisms to keep requested media in the project, accounting for expiring links. Retain originals and version accepted revisions. A preview URL is useful only if it is actually available to the user. Do not claim a remote editor result exists when only a specification was written.

Report what was created, where it is, which tools/settings produced it, what was inspected, and what remains unavailable. Do not make a tool failure a reason to repeat expensive generations or restart the user's entire setup without evidence.
